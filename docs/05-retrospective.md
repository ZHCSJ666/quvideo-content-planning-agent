# 实施复盘（AI 辅助记录）

## 最难的问题

最难的部分是把“模型觉得完成了”转换为可验证的业务完成：计划有四个任务并不代表四份产物存在；脚本存在不代表事实和语言通过审核；保存工具返回前也不能提前宣告成功。当前通过产物状态、任务哈希、独立质量检查、文件写入确认和账本共同判断。

另一个实际难点是模型审核的局限。早期真实案例工程上完成，但二次核查发现 lightweight、durable、环保及国家偏好等没有资料支持的表达。不能因为审核模型打了 4 分就将其当成事实。为此增加面向用户文本的确定性禁用声明规则，明确四条允许的产品事实，并让策略、生成、审核都使用同一事实边界。历史失败保留在 `examples/exploratory/`，不是删掉不理想结果后只展示成功。

## 实际学习与改进

- 工具描述也是 Agent 能力的一部分。初版检索只是英文标签过滤，模型用中文自然语言查询得到空结果，还尝试使用不兼容市场素材。改进为明确支持空查询列举、空结果返回可用标签和下一步建议，保留市场校验。
- “失败重试”与“业务重规划”需要区分。重试仍是同一方案；重规划改变任务策略、素材或服务档位，并必须重新估算和检查依赖。
- 框架检查点不能自动解决业务副作用。额外实现工具回执、同任务锁和原子文件替换，验证重复提交、图重放、跨进程恢复不重复记模拟费用。
- 费用不是最终报价一个数字。失败尝试和被放弃内容也是已花费用；恢复不能清零，替代方案要计算剩余工作。
- 修复依据必须跨计划版本保留。真实运行曾因重规划删除旧产物而丢失审核反馈，反复生成同类错误；现在反馈与有效产物独立存储，修复成功后才清除。
- 恢复边界也要对模型可见。实际模型曾反复修改档位、策略和素材，错误地认为可以重置尝试次数。程序始终保留计数；后续把计数纳入模型观察，并明确返回不可重试及跨计划版本的上限语义。这一失败过程保留，没有改写成合理重规划。
- 模型可以决定停止，但不能代替账本报数字。紧预算案例中的模型建议忽略沉没费用；最终未完成说明现在由程序计算已花费用、最低完成总额和缺口，原始建议仍保留在 Trace 供核查。
- 多文件保存需要明确完成凭证。Markdown 写入失败时不能留下已完成的 JSON；先写说明文档，最后写主清单，失败时保留已审核成果并支持重试。
- 网络超时是真实运行的一部分。早期并行探索出现实际审核超时，改为串行验收并使用经请求验证的 vLLM 参数。真实供应商的超时计费仍是未解决边界，不能冒充本地可保证的 exactly-once。
- 界面只承担解释工作。CLI 和 Streamlit 复用同一服务，界面必须把异常、未完成、Mock 标识和审核拒绝展示出来。

## 下一步

1. 由候选人复跑关键案例，解释一条预算调整和一条失败恢复路径；补充自己的修改和验证记录。
2. 增加独立母语审核或人工标注评估集，验证模型评分与人的判断是否一致；现有模型评分不能证明真实营销效果。
3. 若接入真实商业媒体工具，增加供应商幂等键、作业查询、费用回执和授权元数据验证；再评估并行排期。
4. 扩展不同产品/市场时，先明确产品证据、目标人群和成本规则，避免把当前合成案例的假设固化成真实国家画像。

以上是本次 AI 辅助实施的观察。候选人本人的学习感受、手动代码改动与复跑结果应由本人如实补充，不由 AI 代写成已经发生。
