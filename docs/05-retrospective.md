# 项目复盘与下一步

> 本文结合项目讨论和运行记录整理，由 Codex 协助撰写，正文已由我审阅确认。工程实现、排错和测试执行的分工见 [AI 使用说明](04-ai-usage.md)。

## 最难的是把完成标准落实到每一步

我从一开始就希望项目能交付完整方案。真正展开后，“完成”需要拆成很多可以检查的条件：四条内容是否都存在，引用的素材是否可用，语言和产品事实是否经过检查，费用有没有超限，最后文件是否保存成功。

这些条件之间还有先后关系。比如改了某条任务的策略，就要重新估算，再生成和审核；一条内容被拒绝，其他已经通过的内容应当保留。当前实现用明确的状态和检查来处理这些关系，Trace 则把过程展示出来。我想通过这个项目说明的 Agent 能力，正是对这些中间状态和下一步动作的处理。

## 临时故障案例里有几次不同性质的调整

新的自主恢复案例很适合解释这件事。步骤 8，DE-2 的生成工具返回临时失败；模型随后先查询成本和时间，再选择重试。生成恢复后，审核又拒绝了包含未经证实推断的策略，模型因此修改 DE-2，并保留已经通过的 DE-1。

过程中还出现了一个真实失误：修改计划后，模型直接尝试生成，漏掉重新估算。程序返回 `ESTIMATE_REQUIRED`，这次调用没有扣业务费用。模型看到反馈后补查估算，再继续生成、审核和保存，最后费用是 70，四条方案全部交付。

这条记录说明，不同反馈需要对应不同的动作。服务临时异常可能值得重试，内容不合格需要修改内容或策略，依赖没满足则需要补上前置步骤。当前系统允许模型作出选择，同时由程序检查每一步是否合法。具体步骤见[自主异常处理报告](07-autonomous-failure-paths.md)。

## 停下来也需要有清楚的依据

讨论需求时，我担心工具一直失败，最后什么都交不出来。我的目标仍然是尽可能完整交付，但这也要求系统知道什么时候继续尝试有价值，什么时候已经没有可行路径。

持续不可用案例中，DE-2 返回了不可重试的反馈，并明确当前没有配置替代服务。模型下一步选择停止，保留已审核的 DE-1，记录已花费的 17 个模拟单位，并说明修复服务后可以恢复同一个任务。此时预算和时间仍然充足，停止的依据是必需任务被服务故障阻塞。

这里还要把故障范围说准确：工具明确报错的是 DE-2，US-1 和 US-2 只是还没执行。整单要求四条方案齐备，因此必需任务无法继续时，可以停止后续消耗；不能顺手把其他未执行任务也记成服务失败。最终状态和阻塞说明要以实际工具结果为准。

## 模型的判断需要有程序能够核对的事实

预算这部分给了一个很具体的例子。模型的简要理由里，有时会把预计剩余制作费用说成剩余预算。两者含义不同，最终是否允许执行，应当看实际账本和重新估算的结果。

旧的紧预算案例也出现过类似问题：返工已经消耗了一部分费用，最低完成总费用达到 43，而预算只有 40。这个结果需要保留已完成内容，并明确报告缺口 3。不能在换方案时忘记已经花掉的费用，也不能因为想完成任务就自行增加预算。案例与限制见[评估报告](03-evaluation.md)。

质量审核也有类似边界。早期案例中，同源模型审核曾放过“轻量”“耐用”“环保”等没有产品资料支持的表述，问题由 Codex 的二次核查发现。后续实现增加了确定性检查，并收紧生成与审核的事实范围。这能处理已识别的问题，但自然语言还会有新的表达方式，因此当前审核结果仍需要与产品证据一起看。

## 工程状态会影响模型能不能正确恢复

实施记录里有一个值得保留的教训：修改计划时，如果把原产物和拒绝原因一起清掉，模型就可能再次犯同样的错误。当前实现把审核反馈和有效产物分开保存；生成错误也单独记录，重新报价不会让这个错误凭空消失。

尝试次数同样需要跨计划版本保留。模型换了档位、素材或策略，已经发生的失败尝试仍然存在。代码把计数提供给模型，也检查实际执行上限，避免不停改计划却没有进展。

另外，保存了图状态还不够说明重复执行是安全的。项目通过工具回执、同任务锁和原子写入，处理本地重复调用、费用重复记账及保存失败的问题。这些工程细节由 Codex 实现并测试。它们共同支撑了我在需求阶段提出的“保留成果、失败后继续同一个任务”的要求。具体修复过程见[阶段记录](06-build-log.md)。

## 这次与 AI 协作的方法

我比较看重的做法，是先把一个笼统要求拆成可以讨论的问题。例如“项目要做得漂亮”，最后需要落到市场策略、工具反馈、预算检查、成果保留和停止原因这些具体内容上；“做好异常处理”，则需要用不同错误和不同结果来验收。

我也要求实现按部分推进，每部分完成后先验证。这样，AI 提供方案时可以讨论取舍，报告完成时可以回到实际案例检查。后面要求补跑两条无需人工干预的故障链路，也是沿着这个方式继续收紧证据要求。

我希望这份项目能体现的协作方式是：我负责明确要解决的问题和什么结果可以接受，持续提出疑问与验收要求；AI 负责实现、执行和整理证据。具体实现细节仍需要我在提交前继续审阅，亲自做过的修改和复跑会单独记录。

## 目前的不足和下一步

首先，我需要完成个人代码与案例审阅，亲自复跑关键路径，重点解释预算变化、重规划后保留了什么，以及停止为什么合理。这部分完成后，再补到个人验证记录中。

内容质量方面，我会优先考虑独立的语言审核或人工标注样本，检查模型评分和人的判断是否一致。当前使用同一个模型生成和审核，市场资料也是演示设定；这些结果还不能证明真实投放效果。

异常处理方面，后续可以增加更多真实模型输入，检查连续可重试错误、实际 API 超时和不同约束组合下的表现。目前两条自主案例证明的是固定条件下的实际行为，样本量还不足以给出可靠的成功率。

如果继续接入商业媒体服务，还需要处理供应商幂等键、作业状态查询和实际费用回执。当前已验证的是可控本地工具与模拟账本；外部请求超时后是否已经计费，需要服务方记录来确认。这些属于后续扩展。
